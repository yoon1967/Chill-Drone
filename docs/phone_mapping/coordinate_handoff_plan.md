# 휴대폰 영상의 2D 특징점 좌표·매칭 전달 계획

작성일: 2026-10-22. 사용자 선택: 전달 형식은 아직 미정이며, 같은 점을 여러 프레임에서 연결한 2D 픽셀 좌표로 초안을 작성한다.

현재 확정 수치 입력은 `data/mapping/phone_video/2f1_20261021/`에서 Git으로 공유한다.
아래 `output/` 경로는 기존 실행 기록이며 원본 영상·프레임·DB는 로컬/Drive에 유지한다.
현재 파일은 `run_manifest.json`과 `scripts/phone_mapping/shared_inputs.py`로 찾고 검사한다.

## 목표와 역할

- 박수경: 프레임 준비 → 특징점 추출 → 프레임 간 매칭·기하 검증 → 좌표·대응관계·설정 전달.
- 김수호: 전달 입력 읽기 → 카메라 내부 파라미터 추정/보정 경로 적용 → 카메라 자세·3D 점 복원 → 스케일 보정·치수 평가.
- 본 문서는 새 역할 분담의 초안이다. 김수호의 수신 형식과 사용하는 COLMAP 버전은 아직 합의되지 않았다.

- 주석이 있는 측정 참조 이미지는 특징점 추출 입력에 넣지 않는다.

### 왜 좌표와 대응관계가 모두 필요한가

한 프레임에서 점을 찾으면 이미지 속 위치 `(x_px, y_px)`가 생긴다. 다음 프레임에서 같은 물리적 점을 찾은 뒤 두 관측을 연결해야 3D 복원에 사용할 수 있다. 프레임별 점 번호는 그 프레임 안에서만 유효하다. 서로 다른 프레임에서 번호가 같다는 이유로 같은 점으로 취급하지 않는다.

특징점은 안내문 글자·고정된 문틀·잠금장치 등 영상에서 구분하기 쉬운 무늬의 위치다. 가로·세로를 실측한 모서리와 모든 특징점이 일치할 필요는 없다. 사물함의 반복 무늬와 유리 반사는 잘못된 연결을 만들 수 있으므로 매칭 그림과 기하 검증 결과를 함께 확인한다.

### 전달 파일 초안

| 파일 | 내용 | 수신 측 용도 |
| --- | --- | --- |
| `keypoints.csv` | `frame_id`, 프레임 내 `keypoint_id`, `x_px`, `y_px` | 점의 위치 확인과 사용자 정의 처리 |
| `matches.csv` | `frame_id_a`, `keypoint_id_a`, `frame_id_b`, `keypoint_id_b`, 기하 검증 여부 | 두 프레임의 어느 점이 같은 점인지 확인 |
| `database.db` | COLMAP 원본 특징점·기술자·매칭·기하 검증·카메라/이미지 메타데이터 | 호환 버전의 COLMAP에서 복원 단계로 연결 |
| `frames_manifest.json` | 원본 run_id, 프레임 이름·PTS·크기·체크섬 | 좌표와 원본 프레임 대응 |
| `feature_metadata.json` | 추출기·버전·설정·좌표 규칙·카메라 정보 출처·처리 상태 | 입력 해석과 재실행 |
| `measurement_anchors.json` | 실측 길이의 이름·길이·단위와 같은 끝점의 여러 프레임별 2D 관측 | 복원 후 스케일 적용과 치수 검증 |
| `match_previews/`, `quality_report.json`, 실행 로그 | 매칭 확인 그림, 점/매칭 수, 제외/실패 이유 | 입력 품질과 알려진 한계 확인 |

CSV만으로 COLMAP 복원 명령에 바로 넣을 수 있다고 가정하지 않는다. 사용 버전을 고정한 COLMAP에서 특징 추출과 매칭까지만 실행한 데이터베이스를 기본 호환 경로로 검토하고, CSV는 사람이 읽거나 별도 코드로 활용하는 보조 출력으로 제공한다. 실제 수신 테스트로 호환성을 확인한다.

### 좌표 규칙 초안

- 단위는 픽셀이다. 가로 좌표 x는 오른쪽, 세로 좌표 y는 아래쪽으로 증가한다.
- COLMAP 원본 규칙을 유지한다. 이미지 왼쪽 위 바깥 모서리가 `(0, 0)`, 첫 픽셀 중심은 `(0.5, 0.5)`다.
- 실수 좌표를 보존한다. 화면에 보일 때의 반올림값과 저장값을 구분한다.
- 프레임 내 `keypoint_id`는 0부터 시작하는 특징점 행 번호다. 매칭은 이 번호를 참조한다.
- 좌표는 1920×1080 원본 프레임 기준으로 저장한다. 리사이즈 등 좌표 변환을 사용하면 변환과 원본 좌표 환산을 명시한다.
- 원본 PTS를 유지한다. 파일 번호만으로 촬영 시각을 다시 계산하지 않는다.
- 이 단계에서 3D XYZ, 카메라 자세, 실측 m 좌표는 생성됐다고 기록하지 않는다.

- 빨간 44cm와 파란 136cm의 물리적 끝점을 각각 이름 붙인다. 사용자가 표시한 끝점을 기준으로 하고 보이지 않는 위치를 임의로 채우지 않는다.

- 이 점들은 스케일/치수 검증용이다. 자동 특징점과 구분해 보관하고 김수호의 실제 복원 결과에서 대응·삼각측량 가능 여부를 확인한다.

### 최신 정정: 세로 136cm는 바닥까지

사용자가 새로 올린 사진에 따라 C를 문 아래쪽에서 **받침대 전면 하단의 바닥 접점**으로 바꿨다. 중간에 남아 있는 파란 원은 현재 끝점이 아니다. A/B와 44cm 길이, 원본 프레임·자동 특징점·매칭 DB는 유지한다.

- 현재 기준점 버전은 `2f1_20261021_measurement_anchors_v2_floor`다. 사진·manifest·기준점 JSON/CSV·그림과 기존 입력 ZIP을 새 기준으로 갱신한다.
- 기준 사진 frame_0035의 C는 원본 COLMAP 좌표 (754.5,953.5)다. 다른 4장의 바닥 C는 매끈한 경계에 고유 표식이 없어 구조 정렬을 참고한 추정 후보다. 점선/C?·상태 필드로 구분한다.
- A/B 10개는 기존 검토 좌표다. C는 기준 사진 1개와 추정 4개이며, 모든 C의 `metric_validation_eligible=false`, 높이 선분의 `correspondence_ready=false`다. 같은 바닥점임을 확인하기 전에는 세로 치수 검증에 넣지 않는다. 문과 받침대 전면이 같은 평면이라고 가정하지 않는다.
- 가로 44cm로 첫 3D 복원·스케일 시험은 진행할 수 있다. 136cm 비교는 같은 바닥점을 여러 시점에 대응시키고 안정적으로 복원한 뒤 진행한다. 작은 F 오차도 동일한 실제 바닥점의 정답을 보장하지 않는다.
- Jira -254는 진행 중 유지하고 끝점 관측 완료 체크를 보류한다. 바닥 C 대응 확인과 5단계 전달·수신 검증이 남았다.

### 이전 리비전 1 실행 기록 (세로 끝점 해석 정정 전)

아래의 문 아래쪽 C 및 4단계 완료 판단은 이전 기준의 이력이다. 현재 세로 기준은 위의 바닥 C 리비전 2를 따른다.

- 좌표는 원본 1920×1080, 첫 픽셀 중심 (0.5,0.5) 규칙이다. 정수 픽셀 중심 인덱스의 수작업 선택에 0.5를 더해 표기했으며 서브픽셀 정확도를 뜻하지 않는다. 주석 위치의 추정 오차 반경 3~4px를 남겼고, 실측 도구/실측 오차는 미상으로 기록했다.
- 원본/참조 이미지 체크섬, run_id, DB 이미지 ID·PTS·크기, 좌표 범위·길이/단위·JSON↔CSV를 검사했다. 기존 F에 대한 보조 기하 검사 21건은 최대 sqrt Sampson 오차 약 2.33px였다. 이는 실제 3D/cm 정확도 검증을 대신하지 않는다.
- A/B/C는 수동 기준점 ID로서 SIFT 점 번호와 별도로 보관한다. 특징점 DB에 추가하지 않았으며 원본 프레임·참조 사진·3단계 DB는 그대로 보존했다. 김수호가 카메라 복원 후 등록된 여러 시점의 수동 관측을 이용해 왜곡을 고려한 삼각측량·스케일/치수 검사를 진행해야 한다.
- Jira -254는 **해야 할 일 → 진행 중**으로 변경하고 끝점 좌표 기록 항목을 완료 체크했다. 5단계 패키지·수신 확인과 리뷰·develop MR 머지 조건이 남아 완료로 전환하지 않는다.

## 5단계: 전달 ZIP·로컬 수신 검사 완료 — 김수호 환경 확인 대기

- 입력 run_id `2f1_20261021`에 처리 버전 `features_v1`을 붙이고, 새 결과 폴더 `output/phone_mapping/2f1_20261021_features_v1/`에 보관하는 방안을 사용한다.
- 프레임·좌표 범위·PTS 순서·특징점 인덱스 참조·체크섬·데이터베이스와 CSV의 일치를 검사한다. 빈 결과와 잘못된 참조를 정상 성공으로 기록하지 않는다.
- 원본 프레임과 데이터베이스·CSV·설정·실측 기준점·품질 보고서를 `output/phone_mapping/2f1_20261021_handoff_v1/2f1_20261021_handoff_v1.zip`으로 묶었다. 기존 `first_test.zip`은 입력 준비용이며 3~4단계의 전체 결과를 넘길 때는 새 통합 ZIP을 사용한다. 바닥 C의 사용 제한을 유지해 첫 44cm 스케일 시험을 진행할 수 있게 했다.
- 김수호의 수신 환경에서 이미지 경로와 데이터베이스가 읽히고 복원 단계로 연결되는지 확인한다. 예시 CSV를 만들었다는 사실만으로 수신 호환성이 검증됐다고 보고하지 않는다.
- 완료 조건: 좌표·매칭·설정·프레임이 함께 전달되고 수신 측 읽기/연결 결과가 기록된다.

### 2026-10-22 실행 결과와 인계

- 전달 ZIP은 약 56.7MB이며 원본 31장·영상/manifest·PyCOLMAP 4.2.1 DB·전체 CSV·측정 리비전 2·설정/품질 보고서·확인 그림·수신 검사기와 회신 양식을 담았다. `handoff_manifest.json`은 109개 전달 파일의 SHA-256/크기와 활성 상대 경로를 기록한다. ZIP에는 이 manifest를 포함해 110개 파일이 있다.
- 저장소 밖 임시 폴더에 실제 압축을 풀고 `scripts/check_handoff.py --native`를 실행했다. 원본 31장, 점 178,584개, 114쌍의 매칭 59,175개/기하 검증 52,159개, 후보 트랙 15,196개, 측정 15행과 경로/해시/단위/사용 제한 검사를 통과했다. 원본 DB의 해시는 그대로다.
- 네이티브 DB 읽기와 `DatabaseCache.create`로 SfM 입력 캐시에 이미지 31장·카메라 1개·프레임 31개가 로드됐다. 실제 카메라/3D 복원은 실행하지 않았다. 바닥 높이의 확인 상태를 임의로 true로 바꾸고 파일 해시까지 갱신한 부정 입력도 검사기가 거부했다.
- 로컬 실행 보고서는 전달 폴더의 `local_acceptance_report.json`, 실제 실행 로그는 `local_receiver_check.log`다. 이 결과는 **제작자 환경의 압축 해제/읽기 시험**이며 김수호 환경의 확인이 아니다.
- ZIP 루트 README에 김수호가 실행할 환경/명령을 적고 `recipient_message.md`와 `recipient_receipt_template.json`을 동봉했다. 실제 전달 메시지는 자동 발송하지 않았다. 사용자가 새 ZIP을 전달하고 김수호가 `recipient_receipt.json` 또는 실패 로그를 회신하면 실제 수신 확인을 기록한다.
- Jira -254의 패키지 참조/읽기 항목은 완료 체크하고, 바닥 C 관측·실제 수신 확인·리뷰/머지는 보류한다. -253도 실제 수신 확인 조건이 남아 진행 중이다.

## 6단계: 김수호의 3D 복원과 공동 검증

- 김수호가 카메라 자세와 희소 3D 점을 복원하고 등록 프레임 수·점 수·재투영 오차·실패 로그를 제공한다.
- 기준 길이의 복원 길이를 `d_raw`라고 할 때 스케일 `0.44 / d_raw`를 점군과 카메라 경로에 일관되게 적용한다.
- 다른 세로 길이가 1.36m에 얼마나 가까운지 평가한다. 정확한 끝점 대응을 확보하지 못하면 보정/검증 불가 사유를 기록한다.
- 수경은 실제 결과를 읽고 입력 프레임·좌표·결과가 같은 run_id에 연결되는지 확인한다.
