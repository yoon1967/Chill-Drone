# 실시간 지도 갱신 정지와 구간 보존

2026-11-05 · [S15P31B205-382](https://ssafy.atlassian.net/browse/S15P31B205-382)

## 확인한 원인

사용자가 촬영한 약169초 세션의 565개 복원 기록을 분석했다. 상태는 tracking 233회,
lost 220회, initializing 97회, scale_wait 15회였다. 추적 실패·초기화 동안에는 새로운
유효 좌표가 없으므로 마지막 지도를 유지하며 기다려야 한다. 이 상태와 계산 지연을 구분한다.

첫 유효 프레임의 처리2,500ms 중 사람·공간 인식 첫 추론이1,920ms였다. 깊이 모델은
256px만 준비했지만 실제 지도 입력은384px였고, 의미 인식 모델은 로딩만 하고 첫 추론을
준비하지 않았다. 기존40초 원본 패킷 재생에서도 첫 깊이755ms·의미 인식2,216ms가 측정됐다.

동일한288×384 합성 입력으로 GPU를12초 쉰 뒤 깊이 추론716.5ms, 바로 다음 추론23.9ms를
재현했다. 깊이 모델의 제한된 대기 중 준비 동작을 넣으면 같은12초 대기 뒤77.3ms였다.
대기12초 동안 준비 호출15회·총723ms가 추가됐다. 이 PC의 RTX4050 Laptop/CUDA 환경에서
측정한 동작이며 모든 GPU의 재시작 비용을 보장하는 값은 아니다.

기존 기록의 구간 전환은 다음과 같다. 앞 구간이 삭제된 것이 아니라 화면이 새 구간으로 교체됐다.

| 기록 번호 | 지도 구간 | 화면 점 수 | 프레임 처리 |
| ---: | --- | ---: | ---: |
| 121 → 122 | 0 → 1 | 31,835 → 9,204 | 0 → 1,094ms |
| 223 → 224 | 1 → 2 | 31,716 → 9,939 | 0 → 1,094ms |
| 347 → 348 | 2 → 3 | 27,782 → 8,192 | 0 → 907ms |

새 구간 첫 프레임의 의미 인식45~65ms·통합12~16ms만으로는 전환 때 긴 지연을 설명하지
못한다. GPU 대기 후 재시작을 별도 재현했고, 전환 중 앞 구간 전체 점군을 JSON으로 다시
쓰는54~71ms도 확인했다. 전환 지연 전체를 하나의 원인으로 단정하지 않는다.
기존 화면은 구간 변경 후에도 처음 지도에 맞춘 시점을 그대로 사용했다. 새로운 구간의
원점·배율이 달라지면 점군이 시야에서 벗어나 사라진 것처럼 보일 수 있다.

점 배열 생성은 위치·색상·결합 행을 각각 만들면서 다수의 Python 리스트를 생성했다.
실제31,835점으로70회 비교한 결과 기존 평균35.46ms/P95 85.06ms/최대97.36ms,
단일 행 생성은 평균6.30ms/P95 8.86ms/최대71.47ms였다. GC 최대 정지82.9ms가 관측됐다.
자동 GC를 끄지 않고 중간 리스트를 줄여 부담을 낮춘다.

## 변경 동작

- 알려진 카메라 비율·선택 해상도로 깊이 및 의미 인식 추론을 입력 수신 전에 준비한다.
  프로세스가 재사용되는 동안 이미 준비한 크기는 다시 준비하지 않는다.
- CUDA에서 새 프레임의 자세가 유효하지 않고 마지막 추론 후0.75초 이상 지났을 때만
  준비용 입력을 처리한다. 영상·유효 자세·사람 발견·복원 history로 기록하지 않는다.
- 구간 전환 중 중복 JSON 쓰기를 제거한다. 이미 기록된 NPZ와 색인을 보존하고,
  촬영 종료 후 모든 구간을 `submaps/full-*.json`으로 별도 통합한다.
- 실시간 빈 결과에는 마지막 유효 점군을 유지하고, 오류는 간격을 두고 재시도한다.
  이미지 준비는3초 안에 끝나지 않으면 재시도한다. 렌더링 반복은 입력 대기와 독립적이다.
  사용자가 과거의 빈 기록으로 직접 이동하면 당시의 빈 화면을 그대로 보여준다.
- 새 지도 구간은 시점을 다시 맞춘다. 지도 구간 선택으로 앞 구간의 마지막 기록을 열고
  현재 구간 따라가기로 돌아온다. 다른 좌표계를 정렬된 지도로 가장하여 겹치지 않는다.
  구간 목록은 새 색인 항목만 처리하고 GPU 점 버퍼는 재사용한다.
- 점 배열은 행을 한 번만 생성한다. 위치 반올림·정수 RGB·색상 설정·사람 표시는 유지한다.

## 검증과 한계

마지막 코드로 원본 녹화 첫 부분을155.46초 동안 원래 간격으로 재생했다(요청 범위165초 중
첫 파일에 존재하는 패킷 전체). 입력960×720, 지도384px, 정적32,000점 예산, 실제 모델·추적기를 사용했다.
총624회 미리보기·203회 유효 지도 반영이 완료됐고 입력·처리·브라우저 오류는 없었다.
위치 추적/관측 프레임은 수정 전 재생과 달라졌으므로 수치의 직접적인 배수 비교는 하지 않는다.

| 마지막 재생에서의 측정 | 평균 | P95 | 최대 |
| --- | ---: | ---: | ---: |
| 유효 지도 프레임 깊이 추론 | 50.5ms | 68.1ms | 81.3ms |
| 같은 프레임 사람·공간 인식 | 59.3ms | 76.3ms | 94.0ms |
| 점 배열 조회/생성, 캐시 조회 포함 | 2.9ms | 8.5ms | 159.8ms |
| 디코드부터 브라우저 다음 그리기 추정 | 364.7ms | 469.3ms | 644.4ms |
| WebGL 화면 반복 간격 | 8.54ms | 11.6ms | 76.4ms |

첫 유효 지도 프레임은 깊이79.9ms·의미 인식72.6ms였고 디코드부터 부모 프로세스 전달까지245.4ms였다.
순간적인 할당·GC·기록 비용과 추적 실패 대기는 남아 있다. 모든 지연이0이 되거나 실제 지도
갱신이 화면 주사율과 같아졌다는 의미가 아니다. 위 화면 반복 평균은 약117fps이며 지도 반영률과 별개다.

실제 원본 H.264 패킷의 수신 간격을 재생하고 실제 디코더·ORB-SLAM3·깊이·YOLO·SegFormer·
점 통합·기록·Edge WebGL 경로를 사용한다. 카메라 센서·드론 인코더·무선 구간은 재측정하지 않는다.
같은 입력이라도 실시간 후보 선택과 SLAM 초기화가 달라지므로 반영 프레임 수 차이를
성능 향상 배수나 정확도 향상으로 해석하지 않는다. 영상 자체의 추적 실패를 없애는 변경도 아니다.

브라우저 회귀는 빈 결과·HTTP 오류 중 점군 및 실제 그리기 반복 유지, 원점1,000 차이의
새 지도 시점 보정, 이전 구간 재개봉, 현재 구간 복귀, GPU 버퍼 재사용을 검사한다.
모델 준비 순서·같은 해상도의 재준비 방지·CUDA 대기 작업 제한·CPU 제외·두 지도 history와
최종 submap 보존·RGB 직렬화 형식도 자동 검사한다.

아직 새 코드로 실제 드론을 다시 연결한 확인은 하지 않았다. 새 구간을 기존 구간에 연결하려면
별도의 재위치 인식·구간 정합이 필요하다. 현재 단계는 좌표가 검증되지 않은 구간의 분리 보존이다.
