# 고정 간격 증가와 실시간 점 예산

2026-11-05, 작업: [S15P31B205-381](https://ssafy.atlassian.net/browse/S15P31B205-381).

기본 정적 점 예산과 상한을 **32,000점**으로 정했다. 사람 색상 점은 별도 최대 2,000개이며
사람 복셀과 외곽선 표시는 유지한다. 이 PC의 측정 조건에서 실시간성을 우선한 선택이며 모든 장치의 보편적 최대치는 아니다.

## 간격 증가

복셀 간격을 두 배로 키우는 대신 `.005 × 지도 최초 depth_scale`을 한 번 계산해 고정한다.
깊이 배율 1의 예는 `.04 → .045 → .05 → .055`다. 현재 간격이나 이후 프레임 배율을 곱하지 않는다.
SLAM 좌표는 임의 단위이므로 이 수치를 미터로 해석하지 않는다.
예산 초과 시 고정 증가 폭을 더하고 실제 점 중심을 새 격자에 다시 배정한다. 음수 좌표에도 같은 원점이 적용된다.
점군 통합의 숫자 열 정렬을 사용해 큰 점 예산에서의 복셀 묶기 비용도 줄였다.

## 화면 측정

Windows, Edge headless의 실제 WebGL 렌더러, Intel Iris Xe / ANGLE D3D11에서 측정했다.
창은 1440×1000, 지도 캔버스는 1000×700, 동일한 실제 Tello RGB-D 관측 24개의 점을 사용했다.
정적 점 개수를 정확히 맞추고 같은 사람 정보·빨간 점 1,586개·복셀·외곽선을 함께 표시했다.
외부 재생기 대신 제품의 `progressive-map.js`와 GPU 버퍼를 사용했다.
로컬 HTTP 응답을 초당 10회 받아 JSON 해석·전체 점 갱신·그리기를 실행했다. 후보별 30회 갱신을 3회 반복했고 한 반복은 역순이었다.
수치는 화면 반복 주기의 FPS이며 카메라 수신 FPS나 지도 추론 FPS가 아니다.

| 정적 점 예산 | 실제 표시 점 | 화면 FPS | 프레임 간격 P95 | 점 갱신 P95 | 응답 수신부터 다음 화면 P95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 24,000 | 25,586 | 116.1 | 14.2ms | 11.0ms | 49.7ms |
| 28,000 | 29,586 | 117.1 | 14.3ms | 10.4ms | 48.2ms |
| **32,000** | **33,586** | **116.1** | **15.4ms** | **10.9ms** | **48.6ms** |
| 36,000 | 37,586 | 113.2 | 16.8ms | 12.3ms | 50.0ms |
| 40,000 | 41,586 | 109.4 | 19.4ms | 16.1ms | 56.1ms |
| 48,000 | 49,586 | 104.1 | 23.0ms | 21.0ms | 62.8ms |

기준은 평균 FPS만 높게 유지하는 것이 아니라, 프레임 간격 P95를 60fps의 약 16.7ms 안에 유지하는 것이다.
32,000점은 이 조건을 만족한 가장 높은 시험 후보다. 36,000점은 여유가 사라지기 시작하고
40,000점부터 지연이 명확해져 기본값으로 채택하지 않았다. 더 큰 화면·동시 GPU 작업·다수 사람 등은 다시 측정해야 한다.
예비 8,000~256,000점 비교에서도 64,000점 이상에서 간격 변동이 커졌고 128,000점의 P95는 약 60ms였다.

## 통합 비용

같은 실제 RGB·깊이·분할을 사용하고 카메라 위치만 이동시킨 **합성 포화 시험**도 수행했다.
실제 장시간 비행 궤적이나 공간 정확도 검증을 뜻하지 않는다. 80회 중 초기 10회를 제외하고 측정했다.
32,000점 예산에서 실제 상주 점 수는 평균 30,565개·최대 31,988개였다.
점군 통합과 배열 변환은 평균 46.4ms / P95 76.3ms, 점 배열 JSON 생성은 평균 27.1ms / P95 33.4ms였다.
통합·입출력·모델 시간은 화면 FPS와 다르며 더 많은 점은 지도 갱신 주기도 낮출 수 있다.

시간으로 오래된 정적 영역을 지우지 않는다. 대신 정적 상주 점 수를 제한하고 간격을 점진적으로 늘린다.
촬영 범위가 충분히 커지면 옛 영역과 새 영역 모두 세부 정보가 줄 수 있고, 기록 파일·카메라 경로의 디스크 사용량은 계속 증가한다.

## 실행과 재현

원본 Tello H.264 패킷의 12초 구간도 실제 수신 순서·속도로 loopback에 재생했다.
실제 디코더·GPU 깊이/YOLO/SegFormer·Docker ORB-SLAM3·통합·기록·브라우저 경로를 사용했다.
8,000점과 32,000점 모두 미리보기 43회 후 오류 없이 완료했고 새 정적 메시의 꼭짓점·삼각형은 0이었다.
평균 새 지도 표시 간격은 각각 240.6ms / 248.7ms로 약 4Hz였고 화면 프레임 간격 P95는 11.2ms / 10.9ms였다.
디코드부터 표시까지의 평균은 334.3ms / 460.5ms, P95는 530.6ms / 613.4ms였다.
각 실행에서 선택한 SLAM 프레임과 사람 관측이 달라지므로, 이 두 짧은 재생만으로 지연 차이를 점 예산 하나의 효과라고 단정하지 않는다.
점 수 자체의 비교는 위의 동일 관측·동일 사람 정보 시험을 기준으로 한다. 실제 새 드론 연결·장시간 비행 검증은 아니다.

워크트리 `scripts/start_3d_mapping.cmd`는 이 워크트리에 가상 환경이 없으면 원본 Git 저장소의 `.venv`를 사용한다.
코드·결과 경로는 선택한 워크트리를 유지한다. 모델 캐시도 그대로 사용하며 저장된 SegFormer를 불러올 때 온라인 메타데이터 확인을 하지 않는다.
새 코드 적용에는 기존 서버 재시작이 필요하다.

```powershell
& '<원본 저장소>/.venv/Scripts/python.exe' -B scripts/measure_point_budget.py `
  --history '<기존 복원 결과 폴더>' `
  --budgets 24000,28000,32000,36000,40000,48000 `
  --playwright-module '<playwright 모듈 폴더>' `
  --output output/point-budget-profile.json
```

`--browser-only`와 `--backend-only`로 측정 범위를 나눌 수 있다. 원본 관측은 수정하지 않는다.
브라우저·백엔드 원시 표본·영상 복사본은 보고서에 포함하지 않으며 실행 중 임시 전송 데이터는 종료 시 정리된다.
기존 4,000/8,000/10,000점 파일·개인 색상 설정은 호환된다. 이전 기본 8,000점만 최초 실행에서 새 기본값으로 갱신하고,
그 이후 사용자가 선택한 저부하 점 예산은 다시 덮어쓰지 않는다.

별도 `gateway_map_bridge.py` 연결기는 자체 기본 20,000점 제한을 가진다. 이 경로로 전체 점을 전달하려면
`--max-points 34000`을 지정한다. 게이트웨이의 별도 화면 성능은 이 콘솔 렌더링 측정에 포함하지 않는다.
