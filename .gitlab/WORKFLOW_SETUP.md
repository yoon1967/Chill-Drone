# Jira·GitLab 팀 협업 규칙

담당 작업: [S15P31B205-14](https://ssafy.atlassian.net/browse/S15P31B205-14).
2026-10-22 EC2 구성과 팀 병렬 개발 요청을 반영했다. 과거 서버 부재를 이유로 한 CI 중지 방침은
EC2 검증·배포 CI로 대체한다. 자동 convention 검사·자동 리뷰 댓글·필수 동료 승인은 도입하지 않는다.

## 원본과 역할

| 항목 | 현재 원본 | 변경 원칙 |
| --- | --- | --- |
| 요구사항·담당·우선순위·의존 관계 | Jira | 새 작업은 새 이슈로 분리하고 담당자를 확인한다 |
| 코드·검증 결과·MR | GitLab | 작업 브랜치에서 변경하고 develop MR로 반영한다 |
| 공개 코드·외부 제안 | 향후 GitHub | 공개 전환 계획에 따라 별도 연결한다 |
| 공용 API·데이터 형식 | `contracts/` | 생산자·소비자 영향을 함께 기록한다 |

Jira와 GitLab에 같은 작업의 이슈를 각각 만들지 않는다. GitLab Issues가 필요한 별도 논의는
Jira 링크를 명시한다. 제목·설명·담당의 무제한 양방향 복제를 하지 않는다.

## 팀 작업 순서

1. [담당 작업 지도](../docs/team/JIRA_WORK_MAP.md)와 실제 Jira·MR에서 범위·상태·일정을 확인하고,
   아래 작업 단위 규칙에 따라 이번 요청의 새 이슈를 만든다. 같은 대화의 미완료 동일 작업만 이어 쓴다.
2. 최신 develop에서 이번 Jira 키로 작업 브랜치를 만든다. 완료된 작업의 브랜치·MR을 재사용하지 않는다.
3. [폴더 경계](../docs/team/REPOSITORY_STRUCTURE.md) 안에서 작업하고 파트별 검증을 실행한다.
4. 실제 단일 Jira 키로 커밋하고 원격 브랜치에 push한다. 새 브랜치 이벤트가 해당 해야 할 일을 진행 중으로 바꾼다.
5. develop 대상 MR을 [양식](merge_request_templates/Default.md)으로 작성하고 Squash와 `Delete source branch`를 켠다.
6. 작성자가 이름·키·본문·검증 결과를 확인한다. 동료 리뷰는 필요에 따라 요청하며 필수 대기는 아니다.
7. Maintainer가 변경 내용·검증·충돌을 확인하고 머지한다. develop의 실제 merge 이벤트가 Jira 완료를 처리한다.

로컬 브랜치 생성, 커밋, push, MR 작성 또는 승인만으로 완료라고 하지 않는다.
기존 Jira 담당자는 자동화로 덮어쓰지 않는다. 자동 생성 작업은 작성자가 실제 담당자를 지정한다.
Jira 이슈 작성에는 [작업 양식](../docs/conventions/JIRA_ISSUE_TEMPLATE.md)을 사용한다.

## Jira 작업 단위와 완료 이슈 보존

- 새 대화에서 비슷한 작업을 다시 요청하거나 이전 날짜·지난 일정의 이슈에 대해 재작업을 요청하면
  반드시 새 Jira 이슈를 만든다. 제목·코드·담당자가 같다는 이유로 과거 이슈를 재사용하지 않는다.
- 특히 연결된 develop MR이 한 번이라도 머지됐거나 Jira가 완료 상태이면 해당 작업 단위는 끝난 것이다.
  자동화 지연으로 Jira가 아직 진행 중이어도 MR이 머지됐으면 후속 작업은 새 이슈로 분리한다.
  버그 수정·보완·추가 검증·같은 기능의 재작업도 새 이슈·새 브랜치·새 MR로 진행한다.
- 완료 이슈를 다시 진행 중으로 돌리거나, 머지된 MR·이전 작업 브랜치에 추가 커밋을 쌓지 않는다.
  새 브랜치는 최신 develop에서 새 키로 만들며, 과거 공유 이력은 바꾸지 않는다.
- 같은 대화에서 아직 머지·완료되지 않은 동일 범위의 구현·검증·인계는 현재 이슈·브랜치·열린 MR을
  이어 쓴다. 도구 재시도·자동화 이벤트 재전송·대화 압축은 별도 사용자 작업 요청이 아니다.
- 과거 이슈와의 관련성은 Jira 연결 관계로 남긴다. 새 MR의 제목·본문·브랜치에는 이번 작업 키만 사용해
  과거 이슈가 완료 자동화에 다시 연결되지 않도록 한다. 과거 이슈의 담당·일정·완료 이력은 보존한다.

## 이름과 병합

- 브랜치: `<유형>/<실제 Jira 키>-<소문자-kebab-case>`.
  유형: feature, fix, hotfix, infra, docs, refactor, test, chore.
- 커밋·MR 제목: `<type>(<선택 scope>): [<실제 Jira 키>] <구체적인 변경>`.
  type: feat, fix, docs, style, refactor, perf, test, build, ci, chore, infra.
- 일반 작업은 1 MR : 1 Jira 작업이다. 브랜치·새 커밋에 사용한 키도 MR과 같아야 한다.
  개별 커밋의 키는 생략할 수 있다.
- MR 본문·주석·예시에도 다른 Jira 키를 넣지 않는다. 자동화가 원문 전체에서 키를 추출한다.
  선행 작업은 Jira의 연결 관계에서 관리하고 MR에는 현재 작업 링크와 기술적 의존 조건을 적는다.
- develop/master에 직접 push하지 않는다. 이미 공유한 이력을 force push·reset으로 소급 수정하지 않는다.
- 릴리스 develop→master MR은 릴리스 작업을 별도로 사용하고 포함된 원래 커밋 키를 유지한다.
  현재 상태 자동화의 완료 대상은 develop이며 릴리스 완료 전환은 별도다.

## 일반 develop MR의 소스 브랜치 자동 삭제

2026-10-29 사용자 요청으로 모든 팀원의 에이전트에 적용한다. 프로젝트에 이미 켜진
`Delete source branch` 기본값을 MR 생성·수정·병합 과정에서도 ON으로 유지한다.
일반 develop MR에 자동 삭제를 끄도록 했던 종전 지침은 이 정책으로 대체한다.

- 대상은 이 프로젝트의 임시 작업 브랜치에서 develop으로 보내는 일반 작업 MR이다.
  사용자가 요청한 정상 MR 병합에는 성공 후 해당 원격 소스 브랜치 자동 삭제가 포함되므로
  별도 삭제 확인을 반복하지 않는다. 이 정책 자체가 요청하지 않은 MR의 병합 승인은 아니다.
- 웹 UI에서는 `Delete source branch`/`Remove source branch` 체크를 유지한다.
  REST API의 MR 생성·수정·병합 요청은 `remove_source_branch=true`를 사용하고,
  조회 응답의 `should_remove_source_branch` 등 실제 설정을 확인한다.
  Git push로 MR을 만들 때는 `-o merge_request.remove_source_branch`,
  `glab mr merge`를 사용할 때는 `--remove-source-branch`를 명시한다.
- 도구의 기본 인자·기존 보존 지침·별도 삭제 승인 부재를 이유로 `false`를 보내거나 체크를 해제하지 않는다.
  본인 또는 다른 팀원이 만든 일반 MR에도 같은 기본값을 적용한다. Squash도 기존대로 켠다.
- 병합 직전 대상 브랜치·최신 SHA·검증 결과·충돌과 소스 브랜치의 다른 열린 MR 사용 여부를 확인한다.
  develop/master·기본/보호 브랜치·장기 공유 브랜치·`docs/agent-inbox`, 사용자가 보존을 요청한 브랜치,
  다른 작업이 사용하는 브랜치는 일반 자동 삭제 범위에 넣지 않는다. 예외를 발견하면 병합을 멈추고
  대상과 영향을 설명해 처리 방침을 확인한다. 에이전트가 임의로 기본값을 끄거나 보호를 해제하지 않는다.
- 병합 후 MR의 merged 상태, 이번 Jira 완료 상태, 소스 원격 브랜치 제거 여부를 각각 확인해 보고한다.
  자동 삭제 실패 시 별도 수동 삭제로 우회하지 않는다. 로컬 브랜치·worktree 삭제는 포함하지 않는다.

## 브랜치·MR 삭제·닫기 전 필수 확인

모든 팀원의 에이전트는 아래 절차를 **실행 직전 반드시** 거친다. 로컬·원격 브랜치의 수동 삭제,
MR 영구 삭제·닫기, 일반 develop MR 범위 밖의 삭제와 일괄 정리에 적용한다.
위 일반 develop MR의 병합 후 소스 브랜치 자동 삭제에는 위 기본값 정책을 우선 적용한다.
CLI·API·웹 UI·자동화 호출 등 실행 도구를 바꾸어 이 절차를 생략하지 않는다.
일반 작업 진행·병합에 대한 동료 승인 대기와는 별개로, 삭제·닫기 대상에 대한 사용자 확인이다.

1. **대상과 상태 확인:** 저장소/프로젝트, 정확한 브랜치 이름과 로컬·원격 구분 또는 MR URL/번호,
   최신 커밋 SHA, MR 상태·미병합 변경, 연결된 MR·Jira와 사용 중인 worktree를 읽기 조회한다.
   로컬 변경·미푸시 커밋·다른 작업의 사용 여부와 삭제·닫기 후 영향을 확인한다.
2. **사용자와 생성자 확인:** 원격 작업은 현재 인증된 GitLab 사용자 ID와 생성자의 사용자 ID를 비교한다.
   MR은 GitLab이 기록한 작성자(`author.id`)를 사용한다. 브랜치는 해당 이름의 현재 브랜치를 만든
   최초 push/생성 이벤트 또는 이 세션의 검증된 생성 기록을 사용한다. 같은 이름의 과거 삭제·재생성
   기록과 구분한다. 로컬 브랜치는 생성한 작업 세션·worktree 기록으로 확인하며 원격 생성자와 같다고
   추정하지 않는다. Git 작성자 설정, 마지막 커밋 작성자, 브랜치 이름, Jira 담당자, Maintainer 권한만으로
   생성자를 판정하지 않는다. 조회 권한이나 기록이 없으면 **생성자 불명**으로 처리한다.
3. **판정과 질문:** 아래 기준에 따라 확인 결과·근거·구체적인 실행 계획을 사용자에게 먼저 제시한다.
   생성자가 본인이어도 대상과 영향을 설명하고 삭제·닫기에 대한 명시적 답변을 받아야 한다.

   | 확인 결과 | 에이전트의 처리 |
   | --- | --- |
   | 실행 사용자와 생성자가 같음 | 확인 질문 후 해당 대상·동작에 대한 명시적 승인이 있을 때만 실행 |
   | 타인이 생성함 | 실행 중단. 타인 소유임을 알리고 생성자가 자기 계정으로 처리하도록 안내 |
   | 생성자 또는 실행 사용자를 확인하지 못함 | 실행 중단. 부족한 근거를 알리고 사용자에게 생성 기록·소유자 확인 요청 |

   질문에는 대상, 실행 사용자, 생성자와 확인 근거, 삭제/닫기/자동 삭제 중 동작, 미병합·미푸시 작업,
   연결된 MR·Jira 영향, 복구 가능 여부를 포함한다. 예: “이 브랜치의 생성자는 현재 사용자로 확인됐고,
   연결 MR은 병합됐습니다. 원격 브랜치를 삭제하면 이 브랜치 이름이 사라집니다. 이 대상을 삭제할까요?”
   타인·불명 대상에 대한 단순한 “진행” 답변을 본인 생성 확인으로 바꾸어 해석하지 않는다.
4. **답변 대기와 재확인:** 무응답·시간 경과·일반적인 “정리해 줘”·“머지해 줘”는 승인이 아니다.
   이 정책의 도입 요청도 실제 대상 삭제 승인이 아니다. 이미 같은 대화에서 위 정보와 정확한 대상·동작에
   대해 명시적으로 승인받았고 상태가 같으면 중복 질문하지 않는다. 실행 직전 계정·생성 근거·SHA·MR 상태와
   승인 범위를 다시 비교하고 달라졌으면 다시 확인한다. 대상이 여러 개면 각각 열거하여 일괄 확인받으며
   승인받지 않은 대상을 추가하지 않는다. 승인 대기 중에는 삭제·닫기와 무관한 작업만 계속한다.
5. **실행과 보고:** 허용된 대상·동작만 수행하고 결과를 다시 조회한다. 대상, 생성자 확인 근거,
   사용자 확인 내용, 실제 결과 또는 미실행 이유를 작업 인계에 남긴다. 실패 시 다른 계정·봇·권한 상승,
   보호 해제나 강제 삭제로 우회하지 않는다. 기본/보호 브랜치는 이 정리 절차로 삭제하지 않는다.

일반 develop MR의 소스 브랜치 자동 삭제는 별도 확인 절차 대신 위 ON 기본값 정책을 따른다.
그 밖의 삭제는 기존 체크 상태를 승인으로 간주하지 않는다. 보존 대상이거나 삭제 범위를 확인할 수
없으면 자동 삭제를 임의로 끄고 병합하는 대신 병합을 멈추고 사용자에게 처리 방침을 확인한다.
MR 닫기는 영구 삭제와 구분해 질문하되, 기존 Jira 자동화가 조건에 따라 자동 생성 작업을 영구 삭제할 수
있으므로 해당 이슈와 조건을 확인하고 영향을 설명한다. 소유자 확인을 위해 실제 삭제를 시험하지 않는다.

이 절차는 저장소 지침을 읽는 에이전트의 필수 작업 규칙이다. GitLab 서버의 삭제 권한을 변경하거나
사람의 직접 실행·지침을 읽지 않는 도구를 기술적으로 차단하지 않는다. CI 차단·자동 리뷰 댓글·로컬 hook을
추가하지 않으며, 팀원은 개정본을 받은 후 진행 중인 세션에도 이 절차를 다시 읽힌다.

## 적용한 설정과 범위

| 항목 | 운영 상태 |
| --- | --- |
| develop/master 직접 push | 금지, force push 비활성화 |
| develop/master merge | Maintainer가 검증 후 MR로 수행 |
| Squash | 일반 작업에서 사용 |
| Delete source branch | 일반 develop MR 생성·수정·병합에서 ON 유지 |
| 동료 승인 | 선택 |
| Jira Webhook | 새 브랜치 시작·MR 연결·실제 develop 머지 완료 |
| Custom issue tracker | Jira 프로젝트 및 번호 링크, 2026-10-22 활성화 |
| GitLab CI/CD | EC2 기반 검증·배포 설정 사용, 배포 기반 MR에서 관리 |
| Jira 개발 패널 | GitLab for Jira Cloud 사이트·그룹 연결은 별도이며 아직 연결하지 않음 |

Custom issue tracker는 `S15P31B205-번호`를 Jira로 연결한다. 다른 프로젝트 접두사도 숫자만 추출하므로
이 저장소에서는 타 프로젝트 키를 작업 키로 사용하지 않는다. 이 기능 자체가 상태를 동기화하지는 않는다.
상태 변경은 기존 [Jira 자동화](../automation/jira-mr/README.md)가 담당한다.
이미 승인된 자동 생성 이슈의 MR 닫힘 삭제 조건은 해당 가이드를 따른다. 기존 직접 작성 이슈는 보존한다.

EC2 CI의 코드 검증·배포 성공 여부를 실제 결과로 보고한다. 서버 설정과 저장소 파일 반영은 별개이며
MR 미병합·미실행 항목은 분리해 적는다. 배포 전 검증과 실패 복구는 `docs/EC2_CICD.md`를 따른다.
이 협업 변경은 배포 기반 MR의 `.gitlab-ci.yml`을 CI 중지 설정으로 덮어쓰지 않는다.

## 개인 로컬 환경과 산출물 관리

모든 팀원의 에이전트는 실 프로젝트의 목적에 직접 필요한 작업과 산출물만 유지한다.
개인별 로컬 환경을 백업·보존할지는 사용자의 명시적 요청을 기준으로 하며, 기본값은 만들지 않고 남기지 않는 것이다.

- 별도 백업·보존 요청 없이 개인 PC의 환경·설정·작업 폴더 복사본, `.bak`/`.orig` 파일,
  ZIP·스냅샷·보관 폴더를 만들거나 계속 유지하지 않는다. 기존 변경을 훼손하지 말라는 지침은
  별도 백업 사본을 만들라는 뜻이 아니다.
- 기능 구현·오류 재현과 수정·회귀 방지·빌드/배포·이번 Jira의 완료 조건에 직접 쓰이지 않는
  보존·검증·테스트·리뷰 절차, 임시 스크립트, 개인 환경 진단 기록, 전체 로그, 캡처, 보고서는
  추가하거나 유지하지 않는다. 저장소·MR·Jira에 올리지 않으며 로컬에도 보존하지 않는다.
- `.gitignore`로 숨기거나 저장소 밖·다른 브랜치·별도 worktree·압축 파일로 옮겨 남기는 것도
  보존에 해당한다. 프로젝트와 직접 관련 없는 산출물의 보관 수단으로 사용하지 않는다.
- 실제 작업 실행에 잠시 필요한 임시 입력·출력은 최소한으로 사용하고, 사용이 끝나면 이번 작업에서
  만든 것이 확실한 파일·폴더를 확인해 정리한다. 성공·실패 여부와 관계없이 불필요한 잔여물을 남기지 않는다.
  정리가 실패하면 남은 정확한 경로와 이유를 보고하며 정리됐다고 말하지 않는다.
- 제품 동작을 확인하는 테스트 코드·회귀 재현 자료·필수 CI/배포 검증과 운영 설정 등 직접 필요한
  프로젝트 자산은 유지한다. 검증·테스트·리뷰라는 이름 자체가 제거 기준은 아니다.
  필요한 검증을 수행하고 결과는 MR·Jira에 명령·결과·후속 조치 중심으로 간결히 기록한다.
  의미 없는 검사·중복 테스트·별도 리뷰 보고서·체크리스트를 형식적으로 추가하지 않는다.
- 사용자가 백업·보존을 명시하면 요청한 대상·목적·범위 안에서만 처리한다.
  로컬 보존 요청을 저장소 업로드 승인으로 확대하지 않는다.
- 기존 사용자 원본·미완료 변경·다른 사람의 파일·운영 데이터는 불필요하다고 추측해 지우지 않는다.
  이 정책은 기존 파일의 일괄 삭제 지시가 아니다. 브랜치·MR 삭제/닫기는 해당 별도 절차를 따른다.

## 로컬 검증·보안·인계

- 변경에 직접 필요한 검증과 `git diff --check`를 실행한다. 위 산출물 정책에 따라 임시 출력은 정리한다.
- 협업 문서·CI·템플릿 변경에는 `python -B -m unittest discover -s tests -p test_workflow_policy.py -v`를 실행한다.
  이 검사는 Jira 템플릿을 확인하며 convention·리뷰 승인 강제 장치가 아니다.
- 비밀 변수·API 토큰·웹후크 암호·개인 키·실제 촬영 자료를 저장소·MR·Jira에 복사하지 않는다.
  값 없는 `.env.example`과 공개 가능한 합성 예제를 사용한다.
  사용자 승인에 따라 팀원의 후속 작업에 필요한 확정 수치 입력·설정·검증 기록은 `data/mapping/`에
  회차/버전별로 공유한다. 영상·사진·DB·ZIP·전체 로그는 이 예외에 포함하지 않는다.
- [시작 안내](../docs/team/START_HERE.md)의 인계 항목과 실제 검증 결과를 남긴다.
- [GitHub 공개 전환](../docs/team/GITHUB_RELEASE.md)은 별도 공개 대상·라이선스·이력 점검을 확인한 뒤 수행한다.
