# MoNA-Bench Ubuntu·ROS 통합 실험

담당 작업: [S15P31B205-276](https://ssafy.atlassian.net/browse/S15P31B205-276).

[MoNA-Bench 원본](https://github.com/npu-ius-lab/MoNA-Bench)의 커밋을
`upstream.lock.json`에 고정하고 16개 ROS 패키지를 하나의 워크스페이스로 구성한다.
원본 Ubuntu 18.04·ROS Melodic을 Ubuntu 20.04·ROS Noetic·Python 3 컨테이너로
이식하는 실험이다. 호스트의 ROS 2 Jazzy와는 별개이며 ROS 2 패키지가 아니다.

파이프라인은 카메라 → 단안 깊이(기본 Depth Anything V2 Metric Indoor Small, 선택 SC-DepthV2)
→ 바닥 RANSAC 및 하향 ToF 거리 보정 → ORB-SLAM2 → Fast-Planner → PID이다. TT 확장 보드의 **전방 ToF**와 Tello의
**하향 ToF**는 용도가 다르다. 원본의 거리 보정은 `/tello/tof_btm`을 사용한다.

## 실행

저장소 루트의 PowerShell에서 실행한다. Docker Desktop Linux 엔진과 NVIDIA
GPU 지원이 필요하다. 첫 빌드는 ROS·PyTorch 의존성을 내려받으므로 오래 걸린다.

```powershell
.\modules\autonomy\mona_bench\run.ps1 -Action Build
.\modules\autonomy\mona_bench\run.ps1 -Action Check
.\modules\autonomy\mona_bench\run.ps1 -Action Graph
.\modules\autonomy\mona_bench\run.ps1 -Action Smoke
```

`Check`는 패키지·Python import·launch 그래프·CUDA·모델 파일 유무를 출력한다.
체크포인트가 없어도 설치 검사는 성공할 수 있으므로 `checkpoint_present`와
`cuda_available`을 함께 확인한다. `Graph`는 노드 목록만 읽는다.
`Smoke`는 합성 바닥 포인트클라우드·거리·깊이를 40회 입력해 컴파일한 RANSAC과
스케일 보정 노드 간 타임스탬프 동기화 및 30프레임 이후 발행을 확인한다.
학습 가중치나 실제 기체는 사용하지 않는다.

공식 [SC-Depth](https://github.com/JiawangBian/sc_depth_pl)의 SC-DepthV2 NYU
체크포인트를 `data/outputs/mona-bench/models/sc_depth_v2_nyu.ckpt`로 준비한다.
가중치는 이미지나 저장소에 포함하지 않는다. 현재 원본에서 연결한 OneDrive
파일 다운로드는 404를 반환하므로 가중치를 확보하기 전에는 추론 검증이 미완료다.
출처와 SHA-256을 기록하고 버전·학습 데이터가 일치하는 파일을 사용한다.

2026-11-04: [PINTO의 SC-Depth V2 배포](https://github.com/PINTO0309/PINTO_model_zoo/tree/main/210_SC_Depth_pl)에서
NYU 480×640 ONNX 변환 가중치를 확보했다.
파일은 `data/outputs/mona-bench/models/sc_depth_v2_nyu_480x640.onnx`(57,303,852 bytes),
SHA-256은 `69a555382b152ae71930bef2777d2a3945df666c48f73bc6748873ab5f9e4d84`다.
같은 폴더의 `.onnx.source.json`에 배포 URL과 archive member를 기록했다.
제3자 변환 배포본이며 원저자 체크섬과의 대조는 하지 못했다.
기존 `.ckpt` 로더와 별도로 ONNX 추론 경로를 연결했다. 기본 launch의
`backend:=onnx`는 모델 해시를 검사하고 `depth_device:=cuda`(기본) 또는 `cpu`로 실행한다.
기존 PyTorch 노드는 `backend:=pytorch`로 선택할 수 있다.
원본 PyTorch 체크포인트는 아직 미확보다. 중단한 대용량 묶음은 `.partial`로 표시한다.
ONNX 그래프 검사 및 CPU 추론 검증은 통과했다. 입력 `[1,3,480,640]`, 출력
`[1,1,480,640]`이며 합성 0 입력의 출력은 전부 유한한 양수였다.
검사 기록은 `models/sc_depth_v2_nyu.validation.json`에 있다. 실제 영상 정확도와
MoNA 전체 거리 보정·SLAM·경로 계획을 포함한 추론은 아직 검증하지 않았다.

### 기본 깊이 모델: Depth Anything V2 Metric Indoor Small (2026-11-05)

장애물 녹화에서 SC-DepthV2가 다가오는 장애물 거리를 따라가지 못해(아래 「장애물 녹화」) 기본을
[Depth Anything V2 Metric Indoor Small](https://huggingface.co/depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf)로
바꿨다. Small만 Apache-2.0이며 Base·Large는 비상업(CC-BY-NC-4.0)이라 쓰지 않는다.
출력은 m 단위 거리다. 가중치는 저장소와 이미지에 넣지 않고 호스트에서 ONNX로 변환한다.

```powershell
.\.venv-depth\Scripts\python.exe modules/autonomy/mona_bench/export_da2_onnx.py data/outputs/mona-bench/models
.\.venv-depth\Scripts\python.exe modules/autonomy/mona_bench/export_da2_onnx.py data/outputs/mona-bench/models --precision fp32
```

변환 스크립트는 revision `8078d68a9c75a972131914f6afd0c1723be0da7f`와
`model.safetensors` SHA-256(`e990eb82…04a3`)을 고정한다. torch·transformers·onnx 패키지가 필요하다.
torch 2.11.0·transformers 4.57.6에서 두 번씩 변환한 해시가 같았다. 다른 버전으로 바꾸면 해시가 달라질 수 있다.

| 모델 종류(`-DepthModel`) | 파일 | SHA-256 | 용도 |
| --- | --- | --- | --- |
| `da_v2_metric_indoor_small`(기본) | `da_v2_metric_indoor_small_518x686_fp16.onnx`(49,696,177 bytes) | `f2b7c5b75fc35ecde8681ac1df8c08dd77207ab41d77f4248f6e1fee1b6957a7` | CUDA. 내부 fp16, 입출력 float32. 변환에 CUDA GPU 필요 |
| `da_v2_metric_indoor_small_fp32` | `da_v2_metric_indoor_small_518x686.onnx`(99,117,950 bytes) | `429f8d354187818d1f39d4d3280d948cf29651b75c40c105a2b661142ededbd3` | CPU 추론 |
| `sc_depth_v2_nyu` | 위 SC-DepthV2 ONNX | 위 참조 | 비교용(상대 깊이) |

입력은 Tello 960×720을 518×686(짧은 변 518, 14의 배수)으로 bicubic 축소하고 ImageNet 평균·표준편차로 정규화한다.
출력은 640×480으로 줄여 기존 SC-Depth 토픽으로 발행하므로 뒤 단계는 바뀌지 않는다. launch 인자는 `depth_model`이다.

- 바닥 RANSAC 기준: SC는 상대 단위 0.001(약 6mm)을 쓰고, 미터 모델은 0.01m를 쓴다(`ground_distance_threshold`).
- ONNX와 변환 때 저장한 PyTorch 기준 출력의 상대 오차 99백분위: fp32(CPU) 0.1% 미만, fp16(CUDA) 1% 미만.
- RTX 4050 Laptop CUDA `session.run`: fp32 64ms, fp16 38ms(간격을 둔 호출 55ms·32ms).
  실제 녹화 20장에서 fp16과 fp32의 상대 차이는 중앙값 0.055%, 99백분위 0.26%였다. fp16은 CPU에서도 돌지만 1장 약 1.9초다.

## ONNX 영상 추론 확인

```powershell
.\modules\autonomy\mona_bench\run.ps1 -Action Infer
```

기존 웹 서버에서 0.3초 이내의 최신 영상을 GET으로 읽고 깊이를 추론한다(`-DepthModel`로 모델 선택).
`inference/<회차>/`에 RGB·깊이 배열(`metric_depth` 또는 `relative_depth`)·미리보기·결과 JSON을 저장한다.
이 검사는 하향 ToF 거리 보정이나 자율 이동을 실행하지 않는다. SC-DepthV2 배열은
m 단위가 아니며 지상에서 하향 ToF가 10cm 이하인 경우 거리 보정 입력으로
사용할 수 없다. 아래 정규화 설명은 SC-DepthV2 기준이다.

ROS 노드는 BGR→RGB, resize 640×480, `/255`, 평균 0.45·표준편차 0.225 정규화를
적용한다. `/tello/image_raw`를 구독하고 원래 타임스탬프의 BGR 영상 및 32FC1
상대 깊이를 `/sc_depth_pl/color/image_raw`, `/sc_depth_pl/depth/image_raw`로 발행한다.
기본은 onnxruntime-gpu 1.19.2의 CUDAExecutionProvider다. torch wheel의 CUDA 12·cuDNN 9를
재사용한다. 요청한 장치를 쓸 수 없으면 CPU로 넘어가지 않고 시작 단계에서 실패한다.
`run.ps1`의 `-DepthDevice cpu`로 CPU를 고를 수 있다. 2026-11-04 RTX 4050 Laptop에서 1장당
GPU 0.03~0.07초, CPU 약 0.4초였고, 같은 무작위 영상에 대한 두 결과의 상대 오차는 99백분위 1% 미만이었다.

2026-11-04 ONNX 검증 5개 통과: 색상·정규화 계약, 잘못된 영상·모델 거부,
실제 모델 상대 깊이 추론, 실제 ROS 노드의 RGB 입력→BGR/깊이 출력과 타임스탬프 유지.
기존 입력 검사 7개도 통과했다. 실기 Wi-Fi 연결 후 최신 영상 검증은 아직 필요하다.

## SLAM 카메라 보정 시작 순서

재생 시작 때 첫 영상에서만 CameraInfo가 발행되면 ORB-SLAM2가 카메라 정보를
기다리다 시간 초과 후 `No cam calibration`로 종료할 수 있었다.
`calibration_publisher.py`가 `camera_info` 인자로 지정한 동일 YAML을 읽어
`/mona/camera_info`에 정적·latched CameraInfo를 먼저 제공하도록 수정했다.
SLAM은 이 전용 토픽을 사용하고, 깊이→포인트클라우드 처리는 기존 영상별
타임스탬프의 `/sync/camera_info`를 계속 사용한다. 두 토픽을 섞지 않는다.
해상도·초점거리·행렬 길이·왜곡 계수가 잘못되면 명확히 실패한다.
카메라 색상 설정도 실제 BGR 입력에 맞췄다. 이 수정은 새로운 실기 캘리브레이션을
수행한 것이 아니며, YAML의 원본 샘플 보정값을 실제 기체에 맞추는 작업은 남아 있다.

2026-11-04 받침대 녹화 재생 검증: 입력 영상 102개·하향 ToF 100개를 사용해
거리 보정 깊이 13장과 SLAM 자세 13개를 기록했다. 기존 카메라 정보 시간 초과와
보정값 로딩 오류가 재발하지 않았고, 1002개 점으로 맵이 초기화됐다.
자세의 유한값·깊이와의 타임스탬프 일치·쿼터니언 정규화를 확인했다.
회차 `data/outputs/mona-bench/replays/20261104_005328_17675/`에 결과를 남겼다.
정지·무목표 데이터여서 궤적과 후보 속도 출력은 0개다. 기체 명령은 보내지 않았다.
보정 입력 검증 회귀 테스트 4개도 통과했다.

## 입력 녹화와 품질 검사

기존 웹 서버(Windows 포트 8010)가 받고 있는 영상과 **하향** ToF를 GET 요청으로만
읽어서 ROS 1 bag으로 저장한다. 명령·SDK 진입·영상 시작·이륙을 요청하지 않는다.
웹 서버가 이미 최신 영상과 상태를 수신하고 있어야 한다.

```powershell
.\modules\autonomy\mona_bench\run.ps1 -Action Capture -Seconds 30
.\modules\autonomy\mona_bench\run.ps1 -Action Inspect -Bag C:\recordings\input.bag
```

녹화 중 **Enter**를 누르면 그 시점에서 멈추고 bag·입력 검사·`capture.json`까지 저장한다.
Ctrl+C도 같은 방식으로 저장한다. `-Seconds`는 최대 녹화 시간이며 Enter가 없으면 그때 끝난다.
`capture.json`의 `stop_reason`은 `stop_requested` 또는 `time_limit`이다.

기본 주소 `http://host.docker.internal:8010`은 Docker에서 Windows 웹 서버를 가리킨다.
필요하면 `-Url`로 바꾼다. 녹화 결과는 `data/outputs/mona-bench/captures/<회차>/`의
`input.bag`과 `capture.json`이다. 각 회차를 새 디렉터리에 기록한다.

상태·영상 나이가 0.3초를 넘거나 요청이 0.2초보다 오래 걸리면 해당 샘플을 제외한다.
원시 하향 ToF의 cm를 m로 변환하고, 유효하지 않은 거리와 바닥에서의 0~10cm 값은
제외한다. JPEG 중복을 제거하므로 완전히 정지한 실제 프레임도 일부 빠질 수 있다.
영상 시각은 별도 상태 요청의 서버 수신 시각과 영상 나이로 추정한다. 센서 노출
시각이나 정확히 동기화된 기록이 아니며 HTTP 요청 간 오차가 존재한다.

`Inspect`는 RGB·하향 ToF 각각 유효 메시지 10개 이상, 정상 단위·형식·증가하는
타임스탬프, RGB 80% 이상에서 0.1초 내 하향 ToF 관측을 검사한다. 낮은 입력률은
경고로 남긴다. 조건을 만족하지 않으면 종료 코드 2와 구체적 원인을 출력한다.
가중치 없이도 녹화·입력 검사는 실행할 수 있다. 가짜 서버로 녹화한 자료에는
`source_modes: ["fake"]`를 남기며 실기 자료로 간주하지 않는다.

## 재생

```powershell
.\modules\autonomy\mona_bench\run.ps1 -Action Replay -Bag C:\recordings\trial.bag
```

ROS 1 bag에는 같은 시계의 `/tello/image_raw` (`sensor_msgs/Image`, 색상 영상)와
`/tello/tof_btm` (`sensor_msgs/Range`, m 단위 하향 거리)이 필요하다. 출력과 로그는
무시되는 `data/outputs/mona-bench/`에 저장된다. 촬영 자료를 커밋하지 않는다.
원본 카메라 보정·고정 카메라 각도는 샘플 값이다. 실제 기체에 맞춰 교정해야 한다.

재생은 먼저 입력 검사를 통과해야 하며, 이후 체크포인트를 확인한다. 로그와 입력
검사 결과는 `replays/<회차>/`에 저장하고 재생 중 각 처리 단계의 출력을
`outputs.bag`에 기록한다. 정상 재생 완료 시 `result.json`에 거리 영상·SLAM 자세·
궤적·위치 명령·후보 속도별 메시지 수를 남긴다. 메시지 유무는 정확도나 회피
성공을 증명하지 않는다. 수동 목표 방식이므로 목표 토픽이 없는 bag에서는
궤적·명령이 생성되지 않을 수 있다. 단계가 비어 있으면 성공으로 표시하지 않는다.

기본 기록은 가볍다(`light`): SLAM 자세·odometry·궤적·위치 명령·후보 속도·목표·하향 ToF만 저장한다.
깊이 영상·포인트클라우드·계획기 지도까지 분석하려면 `-RecordDepth`(`MONA_RECORD=full`)를 붙인다.
무거운 토픽을 8~10Hz로 함께 기록하면 1배속 재생이 느려지고 기록기도 메시지를 버린다(아래 「1배속 처리량」).
`light`에서는 거리 보정 깊이를 기록하지 않으므로 `result.json`에 `recorded: false`로 표시하고,
이 단계를 입력으로 쓰는 SLAM 자세 수로 판단한다.

### 목표를 넣은 재생

```powershell
.\modules\autonomy\mona_bench\run.ps1 -Action Replay -Bag C:\recordings\trial.bag -GoalForwardM 1
```

`-GoalForwardM`은 재생 중 첫 `/sync/tf_odom` 자세에서 기체 x축(정면) 방향으로
지정한 수평 거리만큼 떨어진, **시작 높이와 같은** 목표를 `/waypoint_generator/waypoints`에
한 번 발행한다. 원본 Fast-Planner 수동 목표 모드는 높이를 map 기준 1.0m로 바꿨으므로
발행한 높이를 쓰도록 패치했다. 계획기는 -0.1m 아래 목표를 무시하므로 그런 시작 높이는
거부한다. 컨테이너 안의 경로 계획기에만 들어가며 기체 명령 경로는 없다. 계산한 목표와
시작 자세는 `goal.json`과 `result.json`의 `goal`에 남는다.

`-PlayRate`(0.05~1, 기본 1)는 bag 재생 속도이며 처리 시각은 bag 시각을 그대로 쓴다.

- `max_acc` 0.08m/s²에서는 정지 상태의 첫 탐색 단계가 최대 2.6cm만 움직여 0.1m 칸을 벗어나지 못했고

  첫 단계 최대 이동은 0.5×max_vel×init_max_tau = 0.08m(0.2m/s·0.8초, max_acc ≥ 0.25 필요)이므로
  `max_acc`를 0.25로, 탐색 격자를 0.05m로 바꾸고 최고 속도 0.2m/s는 유지했다.
- 수정 후(`replays/20261105_020515_13631`, `20261105_020544_25925`) 탐색 성공 9·11회.
  첫 경로는 디스플레이에서 오른쪽으로 최대 3.9m 돌아 목표로 가고, 사람에서는 지도에 사람이 들어오기 전
  계획되어 직진했다. 두 경로 모두 끝이 장애물과 4~7cm로 가깝다(목표가 장애물 바로 뒤).
- 위 재생에서는 재계획 B-spline이 발산했다(제어점 ±50~270m, 위치 명령 수십 m). 탐색 격자 0.1m로
  되돌려도 같았다. 원인은 Fast-Planner `getSamples`다. B-spline 표본 간격이
  `control_points_distance / max_vel` = 0.5/0.2 = 2.5초로 탐색 구간 길이(0.8초 이하)보다 길었다.
  그런데 표본마다 이전 구간으로 한 칸만 되돌아가서, 남은 음수 시간이 쌓여 표본이 수십 초 거꾸로 외삽됐다
  (진단 출력: 출발 (0.15, -0.55)에서 표본 (45.5, -1.9), (-35.0, -36.4)).
  직접 연결(`reach end`) 경로는 연결 구간이 길어 괜찮았고, 탐색 구간으로 끝나는 `near end`만 발산했다.
  원본 설정(3m/s, 간격 약 0.17초)에서는 드러나지 않는다. `near end`의 끝 속도를 출발 노드에서 읽는 오류도 있었다.
  필요한 만큼 이전 구간으로 되돌아가고 끝 속도는 마지막 노드에서 읽도록 패치했다.
- 패치 후(`replays/20261105_042930_15611`, `20261105_043012_29122`) 계획 성공 38·9회, 새 궤적 실패 0회.
  모든 B-spline 제어점이 12m 이내(대부분 3~6m)이고 재할당 오류도 없다.
- 사람 녹화는 사람이 비켜난 8초 이후 SLAM이 옆으로 1.15m 밀렸다(실제 이동 없음). 움직이는 물체가 SLAM을 흔든다.

> 팽창 경계까지의 값이었다. 실제 장애물과의 거리는 팽창 지도를 같은 크기로 침식해 근사한다(실제보다 보수적).

- 지도 좌표는 손에 든 첫 카메라 자세와 고정 10° 하향 가정으로 정해져 수직이 맞지 않는다. 깊이에서 맞춘 바닥면으로 보면
  카메라는 바닥 대비 8~16° 아래를 보고, 지도 안 바닥은 8~17° 기울어 몇 m 앞에서 비행 높이로 올라온다.
- `floor_filter.py`(기본 켬, `floor_filter:=false`로 끔): 매 프레임 미터 깊이의 아래쪽에서 바닥면을 RANSAC으로 찾고
  (카메라 위쪽 축과 35° 이내, 0.3~3m 아래) 바닥 위 0.15m 이하와 그 아래 픽셀을 0으로 바꿔 계획기에만 보낸다.
  Fast-Planner는 0을 최대 거리까지 빈 공간으로 처리하므로 앞서 잘못 쌓인 바닥 칸도 지운다. SLAM·스케일 보정 입력은 그대로다.
  재생에서 바닥은 1.2~1.7m 아래, 기울기 10~19°로 잡혔고 픽셀의 19~39%를 지웠다. 1장 약 30ms.
- 실시간(1배속) 재생은 CPU 타이밍에 따라 처리 프레임·계획 횟수가 크게 흔들렸다(같은 설정에서 SLAM 자세 39~77개).
  설정 비교는 0.5배속(`-PlayRate 0.5`)으로 했다. 정면 3m 목표, 침식 근사 실제 장애물 기준:

| 설정(0.5배속) | 녹화 | 계획 성공 | 실제 장애물까지 최소 / 중앙값 | 0.3m 미만 계획 | 팽창 영역 통과 | 장애물 칸 |
| --- | --- | --- | --- | --- | --- | --- |
| 바닥 제거 켬 (`replays/20261105_053957_28808`) | 디스플레이 | 12 | 0.54 / 0.73m | 0 | 1% | 2,481 |
| 바닥 제거 켬 (`20261105_054054_14917`) | 사람 | 8 | 0.76 / 0.90m | 0 | 0% | 487 |
| 바닥 제거 끔 (`20261105_054202_199`) | 디스플레이 | 6 | 0.54 / 0.78m | 0 | 3% | 4,879 |

- 바닥 제거로 장애물 칸이 디스플레이 49%, 사람 82% 줄고 계획 성공이 약 2배가 됐다. 모든 계획이 실제 장애물에서 0.54m 이상 떨어졌다.
  1배속에서 보였던 0.1~0.3m 접근은 지도·자세가 늦게 들어온 회차였다. 최적화 가중치(`dist0`, `lambda2`)는 바꾸지 않았다.
- 목표가 장애물과 뒤쪽 벽 사이에 놓여 계획기가 목표를 옆·위로 옮긴다. 회피 경로를 제대로 보려면 장애물 뒤가 비어 있는
  넓은 곳 녹화가 필요하다.
- `send_goal.py`가 가끔 목표를 보내지 못했다. 시뮬레이션 시계를 따르는 `rospy.sleep`을 실제 시간 대기로 바꾸고 진행 로그를 남겼다.

### 1배속 처리량 (2026-11-05)

1배속 재생에서 영상이 일부만 처리되던 원인을 단계별 처리 수와 프로세스 CPU로 나눠 확인했다.

1. 깊이 노드: DA-V2 fp32 `session.run`이 단독 60ms인데 파이프라인 안에서는 85~160ms로 늘어 입력 간격(약 114ms, 8.8Hz)을
   넘었다(구독 큐 1이라 넘으면 버림). **fp16 모델**로 바꿔 38ms가 됐다.

3. 재생 중 무거운 토픽 기록: 기록기가 메시지를 버려(거리 보정 깊이 89%인 초에 원본 깊이 11%) 측정도 틀렸고 부하도 컸다.

## 호환성 및 원본 수정

- 시스템 NLopt 연결과 Noetic PCL용 C++14 적용.
- Fast-Planner 실행 파일이 메시지 헤더 생성 뒤 컴파일되도록 의존성 보완.
- SC-Depth ROS 토픽·체크포인트·장치 파라미터, RGB 추론 입력 적용.
- 바닥 RANSAC의 정수 나눗셈·빈 결과 접근 수정, 입력 타임스탬프 유지.
- 원본 스케일 필터의 중복 append를 제거하고 길이를 10으로 유지. 기존 코드는
  길이가 10을 넘으면 `len == 10` 조건 때문에 거리 영상 발행이 중단된다.
- 잘못된 하향 거리·높이·스케일 샘플을 제외. 기존 큰 스케일 변화 거부 조건 유지.
- Fast-Planner의 반환값 없는 비-void 함수 6곳에 반환문 추가. GCC 9에서 정의되지 않은
  동작이 되어 kinodynamic 탐색 성공 직후 `fast_planner_node`가 종료(exit -11)됐다.
  수정 후 빌드의 `-Wreturn-type` 경고는 0건이다.
- Fast-Planner 수동 목표의 높이 1.0m 강제를 제거하고 발행한 목표 높이를 사용.
- ORB-SLAM2 RGB-D 가상 기준선 지정. orb_slam2_ros는 CameraInfo `P[3]`을 bf(기준선×fx)로 읽는데
  단안 보정의 0이 들어가 `bf: 0`, 가까운/먼 점 기준 0m가 되어 깊이가 추적에 쓰이지 않았다.
  SLAM 전용 `/mona/camera_info`에만 `orb_virtual_baseline_m`(기본 0.075m, ORB-SLAM2 RGB-D 예제의
  bf 40/fx 535와 같음)을 넣어 bf 47.2, 기준 3m가 됐다. 같은 손 이동 녹화에서 SLAM 직진 이동이
  0.15m에서 약 1.5~1.6m로 늘었다(높은 녹화, 1.2·1.5m 연속 녹화의 첫 구간). 큰 회전 뒤 추적
  끊김은 남아 있고, 같은 bag 재생 간 스케일 중앙값이 6.21과 5.46으로 달랐다. 실제 이동 거리와의
  비교는 아직 하지 않았다.
- 바닥 RANSAC 기준 거리를 `distance_threshold` 파라미터로 바꿀 수 있게 했다(미터 깊이 모델용, 기본값은 원본 0.001).
- Fast-Planner `max_acc` 0.08→0.25m/s², 탐색 격자 0.1→0.05m(launch 설정, 이유는 「장애물 녹화」).
- Fast-Planner kinodynamic `getSamples`가 짧은 탐색 구간을 필요한 만큼 거슬러 올라가고, 끝 속도를 마지막 노드에서
  읽도록 수정. 낮은 최고 속도(표본 간격 2.5초)에서 `near end` 재계획 B-spline이 발산했다.
- 계획기 지도 입력 앞에 바닥 제거 노드 추가(`floor_filter.py`, 「경로 여유와 바닥 제거」).

패치는 고정된 소스 문맥이 다르면 실패한다. 빌드 결과의
`/opt/mona_ws/source-manifest.json`에 커밋·패키지·패치 목록을 기록한다.
별도 GPL-3.0 및 하위 구성요소의 라이선스가 적용된다. 특히 SC-Depth의
Monodepth2 인코더에는 비상업 조건이 있으므로 재배포·상용 사용 전에 각 고지를
확인해야 한다. 원본 라이선스는 스테이징 시 보존한다.
